SOC2 Type II and AI Coding Tools: What Auditors Ask in 2026

The specific SOC2 Type II questions auditors ask about AI coding tool usage in 2026, the full evidence package they expect, and how the Pretense audit log maps to each criterion including CC6.7 and CC7.2.

  • 10 mins read

  • |

  • Published Nov 7, 2026

The Audit Landscape Has Changed

Two years ago, SOC2 auditors rarely asked about AI coding tools. The tools were new, adoption was low, and the audit community was still developing a standard framework for evaluating AI tool controls.

In 2026, it is a standard line of questioning. If your engineering team uses Copilot, Cursor, Claude Code, or any AI coding assistant, expect your next SOC2 Type II audit to include a dedicated review of how you control that usage.

This post covers the specific questions auditors ask, the evidence they expect, and how to be prepared.

The Relevant Trust Service Criteria

SOC2 Type II evaluates five Trust Service Criteria: Security, Availability, Processing Integrity, Confidentiality, and Privacy. AI coding tool usage touches multiple criteria.

CC6.7 (Logical and Physical Access Controls): "The entity restricts the transmission, movement, and removal of information to authorized internal and external users and processes, and protects it during transmission, movement, or removal to meet the entity's objectives."

This is the primary criterion for AI tool usage. Sending code to an LLM API is a transmission of information. CC6.7 requires demonstrating that this transmission is controlled and that the information is protected.

CC7.2 (System Operations): "The entity monitors system components and the operation of those components for anomalies that are indicative of malicious acts, natural disasters, and errors affecting the entity's ability to meet its objectives."

Auditors use CC7.2 to ask about monitoring: how do you detect unauthorized AI tool usage, and how do you respond when you find it?

C1.1 and C1.2 (Confidentiality): "The entity identifies and maintains confidential information to meet the entity's objectives related to confidentiality" and "The entity disposes of confidential information to meet the entity's objectives related to confidentiality."

If your service commitments include protecting customer data or system architecture details, C1.1 and C1.2 require demonstrating that AI tool usage upholds those commitments.

What Auditors Ask

Based on the pattern of questions from auditors at major firms, here is what to prepare for:

Q1: Do your engineers use AI coding assistants?

The answer is almost certainly yes. Auditors know this. The question is establishing the baseline.

Preparation: Have a documented inventory of approved AI tools. This is the tool approval list from your security policy. If you lack one, create one before the audit. An informal "yeah, people use Copilot" is a red flag.

Q2: What controls prevent unauthorized transmission of confidential information through AI tools?

This is the core question. Auditors are asking about CC6.7 compliance for AI tool traffic.

A policy statement alone falls short. Auditors want a technical control: something that enforces the policy automatically, independent of developer judgment.

Strong answer: "We deploy Pretense as a mandatory proxy for all LLM API traffic. It mutates proprietary identifiers before transmission and swaps detected secrets for stand-ins. The proxy is enforced through CI/CD gates. Every API call from the development environment routes through the proxy."

Weak answer: "We have a policy that asks developers to keep confidential code out of AI tools."

Q3: How do you monitor AI tool usage?

CC7.2 asks about monitoring. Auditors want to see that you can detect anomalies: sessions that bypass the proxy, unusual data volumes, new endpoints being used.

Preparation: Demonstrate the audit log. Show the auditor a sample report from pretense audit. Show them how you would detect an unproxied session. Show them the alert mechanism for secret detection events.

Q4: Show me evidence that controls were operating effectively during the audit period.

Type II audits require evidence over time, beyond a single snapshot at the audit date. Auditors will request a sample of audit log entries from across the audit period (typically 6 to 12 months) to verify that controls were applied consistently.

Preparation: Run pretense audit --format csv --limit 100000 before the audit fieldwork begins. This produces a comprehensive report showing every session, every mutation, and every secret detection event over the full year.

Q5: What is your response procedure for an AI tool incident?

Auditors want to see that you have thought through what happens if a developer bypasses controls or if a secret detection event occurs.

Preparation: Document a brief incident response procedure specifically for AI tool events. Secret detection events should generate an alert, be reviewed within 24 hours, and be documented in your incident log.

The Evidence Package

For a complete SOC2 Type II evidence package for AI tool controls, prepare these artifacts:

1. Policy document: Your AI coding tool usage policy, including the approved tool list, data classification requirements, and enforcement mechanism. Should be version-controlled and show when it was last reviewed.

2. Technical control description: A one-page description of how Pretense operates as the enforcement layer. This should describe which identifiers get mutated and swapped back, which secrets get swapped for stand-ins that stay in the answer, and how the audit log is generated.

3. Audit log sample: A CSV or JSON export of audit log entries from the audit period. Auditors will sample these for consistency and look for gaps (periods with zero logs despite active development).

4. CI/CD gate configuration: Evidence that the proxy enforcement is embedded in your pipeline, beyond a recommendation. A screenshot of the pipeline configuration or the relevant pipeline-as-code section.

5. Incident log: Any secret detection events or policy exceptions during the audit period, with documentation of the review and resolution.

This evidence package answers all five common audit questions and provides Type II evidence (operating effectiveness over time) on top of design adequacy.

Common Gaps Auditors Find

Gap 1: Policy exists, technical enforcement is missing

Many organizations write an AI tool policy after their first SOC2 audit flags the gap, but implement only a policy document and skip the technical control. At the next audit, the policy is present but the auditor finds zero evidence that it was enforced. The gap persists.

Solution: Deploy a technical control (Pretense) and generate audit logs from day one.

Gap 2: Audit logs exist but have gaps

If the Pretense proxy is deployed as optional, developers who opt out of using the proxy generate zero logs. Auditors treat unexplained gaps in audit logs as evidence that the control was failing to operate effectively.

Solution: Enforce proxy routing through the CI/CD gate. Make the proxy mandatory.

Gap 3: Incidents left undocumented

Secret detection events that go undocumented and unreviewed leave an incomplete record. If an auditor finds detection events in the proxy logs but zero corresponding entries in the incident log, it appears that the team has stopped monitoring its own controls.

Solution: Set up automated alerting for secret detection events and document each review, even if the review is brief (for example, "developer sent a test file with a hardcoded credential, remediated by moving to environment variable").

Gap 4: Policy left unreviewed since initial creation

Auditors check policy review dates. A policy written in 2024 that has sat unreviewed since is evidence that the organization has stopped actively managing the control.

Solution: Schedule an annual review of the AI tool policy. Document the review in your policy management system.

The Pretense Audit Log as SOC2 Artifact

The Pretense audit log is designed to meet SOC2 evidence requirements with the tooling you already have. Each log entry includes:

  • -Timestamp (ISO 8601)
  • -Session identifier
  • -Developer identifier (if configured)
  • -File path(s) processed
  • -Model endpoint
  • -Mutation count
  • -Secrets swapped count
  • -PHI patterns detected count
  • -Identifier round-trip fidelity percentage

The export format (CSV or JSON) is auditor-friendly and integrates with standard GRC platforms including Drata, Vanta, and Secureframe.

Run before fieldwork:

pretense audit --format csv --limit 100000 > soc2-evidence.csv

The resulting file is the primary artifact for AI tool control evidence.

How I run Pretense on my own code

I build Pretense with Claude Code, and my sessions run through it. Here is the setup I give a new engineer, in order.

  1. -Run the agent through the proxy. Type pretense run claude where you would type claude. It starts a local proxy on port 9339, points Claude Code at it and stops the proxy when the session ends. Detected secrets and PII leave the laptop as stand-in tokens.
  2. -Put hooks on every repo. pretense install adds a pre-commit and a pre-push hook. A key that never lands in git is a key an agent never reads.
  3. -Scan before an agent reads the repo. pretense scan path . lists what it finds. In CI, pretense scan ci exits 0 when clean, 2 on findings and 3 when it examined nothing. Treat 3 as a failure.
  4. -Preview the swap. pretense review . shows what would be mutated. pretense mutate <file> --preview prints one file mutated and leaves the file on disk as it was.
  5. -Round-trip a file you need to share. pretense mutate <file> --map <map> swaps the secrets in place. pretense reverse <file> --map <map> turns it back into the original, byte for byte, from the encrypted map on your machine. We run that round trip on real files before every CLI release and compare sha256 hashes.

One thing I learned the hard way: inside a session the agent sees stand-ins, so a file the agent writes can hold a stand-in where you expected a real value. Grep what the agent wrote before you ship it.

What Pretense will not do is put a secret back into the model's answer. Code identifiers come back byte-exact. Secrets and PII stay as stand-ins in the response. That is deliberate: a prompt-injected model can echo a token into a link, and reversing it there would hand over the real key.

What this means if you own compliance

The outcome: a technical control for AI coding tools that you can show an auditor. Pretense helps with SOC 2, HIPAA, PCI DSS and GDPR evidence. It maps to controls. It does not certify you.

  • -Pin the preset you report against. pretense scan path . --policy soc2 applies that framework's detectors. SOC 2 and PCI presets come with Startup. HIPAA, GDPR and NIST presets come with Enterprise.
  • -Export the evidence. pretense audit --format csv --framework HIPAA writes the events that map to HIPAA. Attach the file to the control with the date range you sampled.
  • -Test detection on your own data. Coverage varies by data type. Run pretense review . on a regulated repo, read the result and record the gaps in your risk assessment.
  • -Keep the policy and the control in step. Your AI tool policy says what engineers may send. pretense run claude and the git hooks are how you show it happens.
