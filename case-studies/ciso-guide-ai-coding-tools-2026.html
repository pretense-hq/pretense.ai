The CISO's Guide to Approving AI Coding Tools in 2026

How security leaders should evaluate and roll out AI coding tools while keeping IP exposure under control. Covers the policy gap (67% of enterprises lack a formal AI coding policy), risk matrix by tool, a 5-question approval checklist, what to log, and incident response when code does leak.

  • 10 mins read

  • |

  • Published Nov 7, 2026

The Policy Gap

A 2025 survey of enterprise security teams found that 67% lacked a formal policy governing AI coding tool usage. The cause is speed, far more than any lack of awareness among security leaders: the tools moved faster than the policy frameworks.

The typical timeline at enterprise companies: developers began using Copilot and Cursor in mid-2024, often with informal approval or under personal accounts. Security teams became aware of the practice during routine audits in late 2024. By the time a formal evaluation began, the tools were already deeply embedded in engineering workflows.

This guide is for CISOs who are now in that evaluation phase: trying to formalize governance over tools that are already in use, or trying to get ahead of adoption before it becomes ungoverned.

The Actual Threat Model

Before building a policy, you need an accurate threat model. Most security leaders I speak with have one of two framings that are both incomplete.

Framing 1: "AI tools are dangerous, we should block them."

This framing misses that blocking popular developer tools leaves the behavior intact and drives it underground. Teams that issue blanket AI tool bans consistently see an increase in developers using personal accounts and web-based interfaces, which are harder to monitor, audit, and control than API-routed tools. Guarded adoption works better.

Framing 2: "AI vendors have enterprise agreements with data protection clauses, so we are covered."

This framing misses the residual risk. Enterprise data protection agreements typically cover intentional data use and training. They leave out breach scenarios (if the vendor is compromised, your data was already transmitted), inference attacks (pattern analysis across anonymized request sets), and the risk of a developer accidentally including a secret in a prompt (contractual protection leaves exposed credentials exposed).

The accurate framing: AI coding tools create a new data exfiltration channel that requires active controls on top of contractual protections. The primary threat is the normal use of the tools creating inadvertent exposure that would have been unacceptable in a pre-AI world, more than malicious use by the vendor.

Approval Framework: 5 Questions Before Approving Any AI Coding Tool

Question 1: Is the traffic API-routed or browser-based?

API-routed tools can be controlled at the network layer with a proxy like Pretense. Browser-based tools require different controls (extension policies, network filtering, acceptable use training). Treat these as separate risk categories.

Question 2: What data categories are transmitted in a typical session?

For each tool, map a typical developer session: what files are read, what context is sent, what the largest possible context window contains. For Claude Code, a typical session can include hundreds of files and terminal output. For Copilot, it is typically the current file and a few open files. The exposure surface is different.

Question 3: Does the vendor offer a data processing agreement (DPA) with appropriate provisions?

Minimum requirements: data retained only for the session, training opt-out honored for all tiers you are purchasing, breach notification within 72 hours, data residency options for regulated industries. For healthcare and financial services, verify if PHI/PII provisions are covered under the DPA.

Question 4: Is there a technical control layer, or are you relying solely on contractual protections?

Contractual protections fail silently. A technical control (mutation proxy, network filtering, browser extension policy) provides verifiable enforcement. For any tool approved for use on proprietary or regulated code, require a technical control layer.

Question 5: What does the audit trail look like?

You need to be able to answer: which identifiers were transmitted to which vendor, when, by whom, and whether they were protected. Producing this evidence is what lets you satisfy SOC2 CC6.7, ISO 27001 A.13, or HIPAA technical safeguard requirements for AI tool usage.

What to Log, What to Alert On

Log everything:

  • -Every outbound request to LLM API endpoints (Anthropic, OpenAI, Azure OpenAI, Google Vertex)
  • -The session ID, user/machine identifier, model used, and timestamp
  • -Whether a technical protection layer (mutation) was active for the request
  • -Any secrets or high-risk patterns detected and swapped for stand-ins

Alert on:

  • -Requests to LLM endpoints that bypassed an approved proxy
  • -Secrets scanner findings (any API key, credential, or token detected in a prompt)
  • -High-volume sessions (single session with unusually large context window size, which may indicate bulk code exfiltration)
  • -Requests from machines that are still waiting to be onboarded to the protection layer

Keep out of alerts:

  • -Volume alone (developer productivity requires high-frequency AI usage)
  • -Specific code content (your SIEM needs only metadata, while the actual code stays out of it)

Incident Response: What to Do When Code Does Leak

Define "leak" before you need to invoke this plan. Recommended definition: an outbound API request that contained proprietary code identifiers while the mutation or redaction layer was inactive.

Immediate (0-4 hours):

  1. -Identify the session: which machine, which developer, which tool, what timestamp
  2. -Pull the full request log for the session from your proxy or network capture
  3. -Assess what was transmitted: which files, which identifiers, whether any secrets were included
  4. -If secrets were included: rotate immediately, ahead of any further analysis.
  5. -Notify the vendor in writing if the incident involved PHI, PCI-scope data, or trade secrets (required under most DPAs)

Short-term (4-48 hours):

  1. -Determine root cause: was this a misconfiguration (developer bypassed proxy), a tooling failure (proxy had a bug), or a policy gap (this category of tool sat outside the policy)?
  2. -Preserve logs for potential legal action
  3. -If trade secrets were transmitted: consult with legal counsel on disclosure requirements and IP protection options
  4. -Brief the affected engineering team lead. Hold the company-wide briefing until you understand the scope.

Long-term (48 hours - 30 days):

  1. -Close the root cause gap: reconfigure, patch, or update policy
  2. -Run a full audit of similar sessions that may have had the same gap
  3. -Update your SOC2 or ISO 27001 control documentation to reflect the incident and remediation
  4. -Consider whether the incident requires disclosure in your next compliance audit

    Yes -> Is there a structured audit trail?
      Yes -> APPROVE with documentation
      No -> CONDITIONAL APPROVAL pending audit trail implementation
    No -> CONDITIONAL APPROVAL pending technical control deployment
  No -> Is it browser-based only?

    Partially -> Approve API use with controls, restrict browser use

Most AI coding tools can be approved with appropriate controls. The goal is to make adoption auditable and technically controlled, while letting it proceed.

A Note on the 67% Gap

The 67% of enterprises that lack an AI coding policy may carry about the same risk as those with written policies. A written policy on its own is documentation of intent; a control requires technical enforcement.

The real question goes beyond "do you have a policy?" It is "can you prove that your policy was followed, with machine-readable evidence, for every AI coding session in the last 90 days?"

Until the answer is yes, the policy is incomplete regardless of how well-written it is.

How I run Pretense on my own code

I build Pretense with Claude Code, and my sessions run through it. Here is the setup I give a new engineer, in order.

  1. -Run the agent through the proxy. Type pretense run claude where you would type claude. It starts a local proxy on port 9339, points Claude Code at it and stops the proxy when the session ends. Detected secrets and PII leave the laptop as stand-in tokens.
  2. -Put hooks on every repo. pretense install adds a pre-commit and a pre-push hook. A key that never lands in git is a key an agent never reads.
  3. -Scan before an agent reads the repo. pretense scan path . lists what it finds. In CI, pretense scan ci exits 0 when clean, 2 on findings and 3 when it examined nothing. Treat 3 as a failure.
  4. -Preview the swap. pretense review . shows what would be mutated. pretense mutate <file> --preview prints one file mutated and leaves the file on disk as it was.
  5. -Round-trip a file you need to share. pretense mutate <file> --map <map> swaps the secrets in place. pretense reverse <file> --map <map> turns it back into the original, byte for byte, from the encrypted map on your machine. We run that round trip on real files before every CLI release and compare sha256 hashes.

One thing I learned the hard way: inside a session the agent sees stand-ins, so a file the agent writes can hold a stand-in where you expected a real value. Grep what the agent wrote before you ship it.

What Pretense will not do is put a secret back into the model's answer. Code identifiers come back byte-exact. Secrets and PII stay as stand-ins in the response. That is deliberate: a prompt-injected model can echo a token into a link, and reversing it there would hand over the real key.

What this means if you buy security

The outcome: your engineers keep their AI coding tools, and detected secrets and PII leave each laptop as stand-in tokens.

  • -The control sits on the endpoint. The swap runs on the developer's machine before the request leaves. No shared gateway holds every team's keys.
  • -You get evidence, not a memo. pretense audit --format csv exports every mutation event. Add --framework SOC2 to keep only the events that map to that framework.
  • -Check it on your own code. Detection is pattern and entropy based, and coverage varies by data type. Run pretense review . on a real repo and read what it catches before you sign off.
  • -Start with one team. One repo, pretense run claude, one week. Then read the audit log with the team lead.
