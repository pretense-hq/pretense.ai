How Pretense Works: A 5-Minute Technical Overview

A clear, visual walkthrough of Pretense's request flow, mutation algorithm, and 30-second deployment. After reading this, you know exactly what Pretense does and how to run it.

  • 8 mins read

  • |

  • Published Nov 7, 2026

The One-Sentence Version

Pretense sits between your IDE and the LLM API, swapping proprietary identifiers and detected secrets for deterministic stand-ins before the prompt leaves your machine, then swapping identifiers back byte-exact in the response so you get working code back.

The Request Flow

Every request your IDE sends to an LLM passes through a sequence that takes roughly 2-5 milliseconds of overhead:

IDE / Claude Code
      |
      v
Pretense Proxy (localhost:9339)
  - Extract code blocks from prompt
  - Scan identifiers (functions, variables, classes)
  - Mutate: getUserToken -> _fn4a2b
  - Swap detected secrets, API keys, tokens for stand-ins
  - Store mutation map locally
      |
      v
LLM API (Anthropic / OpenAI / Google)
  - Receives only synthetic identifiers and stand-ins
  - Proprietary names stay on your machine
      |
      v
Pretense Proxy (reverse pass)
  - Parse response for synthetic identifiers
  - Reverse identifiers: _fn4a2b -> getUserToken
  - Secrets stay as stand-ins by design
  - Return clean, real code to IDE
      |
      v
IDE / Claude Code
  - Receives working code with real names

The proxy is transparent. Developers keep their workflow exactly as it is. The one addition is a single environment variable.

What Gets Mutated

Pretense mutates code identifiers, specifically the names that make your codebase proprietary:

  • -Function and method names: getUserToken, verifyJwtClaims, processPayment
  • -Variable names in function scope: authPayload, sessionConfig, retryCount
  • -Class and interface names: AuthService, PaymentProcessor, UserRepository

Alongside identifiers, Pretense swaps detected secrets, API keys, and tokens for stand-ins, and flags emails and phone numbers by default.

Pretense leaves these as written:

  • -String literals (may contain user-visible content; mutating them breaks output)
  • -Comments (preserved verbatim for context)
  • -Type annotations (structural context for the model)
  • -Import paths (required for LLM to understand module structure)

This is a deliberate trade-off. The goal is to protect what is uniquely yours, which is identifier names that reflect your architecture and domain model, while keeping enough context for the LLM to produce useful output.

The Mutation Algorithm

Pretense uses a deterministic 4-character hex hash derived from each identifier string:

// Simplified algorithm
function mutate(identifier: string, kind: 'fn' | 'v' | 'cls'): string {
  const hash = sha256(identifier).slice(0, 4); // PretenseMut: _fn4a2b
  return `_${kind}${hash}`;
}

// Examples
mutate('getUserToken', 'fn')    // -> _fn4a2b (always)
mutate('authPayload', 'v')      // -> _v9k1m  (always)
mutate('AuthService', 'cls')    // -> _cls5b7a (always)

Determinism is the key property. The same identifier always maps to the same synthetic. This enables:

  1. -Exact reversal: After the LLM responds, Pretense looks up every synthetic identifier in the stored map and swaps it back byte-exact. Secrets stay as stand-ins by design, so a prompt-injected model has only a placeholder to exfiltrate.
  2. -Cross-session consistency: If you ask Claude about getUserToken in five separate sessions, it always sees _fn4a2b. The LLM builds coherent understanding across sessions while the real name stays on your machine.
  3. -Auditability: Every mutation entry is logged with timestamp, file path, identifier, synthetic, model used, and user.

The mutation map is stored locally at .pretense/mutation-map.json and stays on your machine, off every server, including Pretense's own infrastructure.

Deployment in 30 Seconds

# Step 1: Install the CLI globally
curl -fsSL https://pretense.ai/install.sh | sh

# Step 2: Initialize in your project
cd your-project
pretense init

# Step 3: Start the proxy
pretense start
# Pretense proxy running on localhost:9339
# Mutation engine initialized
# Provider: Anthropic

# Step 4: Route your AI tool through Pretense
export ANTHROPIC_BASE_URL=http://localhost:9339
claude "refactor src/auth/token-service.ts"

That is the complete setup. Your IDE configuration stays as it is, with zero policy files to write and zero team rollout plan to run. The proxy intercepts API calls at the network level.

For Cursor, Copilot, and other OpenAI-compatible tools, set OPENAI_BASE_URL=http://localhost:9339.

What Pretense Protects Against

Code exfiltration: If an attacker compromises your LLM provider's infrastructure (or your API keys), they see only synthetic identifiers and secret stand-ins. Reconstructing your proprietary architecture requires the mutation map, which stays on your machine.

IP theft via provider data use: Most AI providers train on API traffic until you opt out. Whatever your opt-out status, Pretense keeps your real identifiers on your machine from the start, so your protection rests on a technical control over a contractual promise.

Compliance violations: HIPAA, SOC2, and PCI-DSS all have provisions about transmitting sensitive system details to third parties. Pretense's audit trail documents every mutation, giving your compliance team proof that proprietary identifiers were protected.

Shadow AI exposure: Developers using personal accounts or unapproved tools will still send code to LLMs. Pretense can be deployed as a team-wide proxy with a CI gate that blocks unprotected API calls, bringing shadow AI usage into compliance while the tools stay available.

Where Pretense's Coverage Ends

Intentional code sharing: Pretense protects API-routed traffic. Proprietary code pasted into a web-based chat interface (ChatGPT.com, Claude.ai) travels outside the proxy and calls for a separate control.

Plain text prompts: If a developer types "our getUserToken function works by..." in a freeform prompt, Pretense parses it as prose and passes the name through as written. Pretense is a code firewall, distinct from a general DLP tool.

Secrets in prose context: If a developer pastes an API key into a markdown file that gets sent as context, Pretense's secret scanner catches it and swaps it for a stand-in; identifier mutation applies to code, so the surrounding free-form text passes through as written.

The Audit Trail

Every mutation session writes a structured log entry:

{
  "timestamp": "2026-04-01T14:32:11Z",
  "session": "sess_7f2a",
  "file": "src/auth/token-service.ts",
  "model": "claude-opus-4",
  "mutations": [
    { "original": "getUserToken", "synthetic": "_fn4a2b", "kind": "fn" },
    { "original": "AuthService",  "synthetic": "_cls5b7a", "kind": "cls" }
  ],
  "secretsSwapped": 1,
  "roundTripFidelity": "byte-exact"
}

Run pretense audit to view session history. Run pretense audit --format csv to produce a report suitable for SOC2 evidence packages.

The audit log is the artifact your compliance team needs. It proves that every API call went through protection, which identifiers were protected, and when.

How I run Pretense on my own code

I build Pretense with Claude Code, and my sessions run through it. Here is the setup I give a new engineer, in order.

  1. -Run the agent through the proxy. Type pretense run claude where you would type claude. It starts a local proxy on port 9339, points Claude Code at it and stops the proxy when the session ends. Detected secrets and PII leave the laptop as stand-in tokens.
  2. -Put hooks on every repo. pretense install adds a pre-commit and a pre-push hook. A key that never lands in git is a key an agent never reads.
  3. -Scan before an agent reads the repo. pretense scan path . lists what it finds. In CI, pretense scan ci exits 0 when clean, 2 on findings and 3 when it examined nothing. Treat 3 as a failure.
  4. -Preview the swap. pretense review . shows what would be mutated. pretense mutate <file> --preview prints one file mutated and leaves the file on disk as it was.
  5. -Round-trip a file you need to share. pretense mutate <file> --map <map> swaps the secrets in place. pretense reverse <file> --map <map> turns it back into the original, byte for byte, from the encrypted map on your machine. We run that round trip on real files before every CLI release and compare sha256 hashes.

One thing I learned the hard way: inside a session the agent sees stand-ins, so a file the agent writes can hold a stand-in where you expected a real value. Grep what the agent wrote before you ship it.

What Pretense will not do is put a secret back into the model's answer. Code identifiers come back byte-exact. Secrets and PII stay as stand-ins in the response. That is deliberate: a prompt-injected model can echo a token into a link, and reversing it there would hand over the real key.

What this means if you lead an engineering team

The outcome: your team keeps asking AI assistants about real systems, configs and connection strings, and detected secrets leave each laptop as stand-ins.

  • -No new workflow. Engineers type pretense run claude in place of claude. Other AI CLIs run the same way, for example pretense run gemini.
  • -Guard the repo as well as the prompt. pretense install adds pre-commit and pre-push hooks. pretense scan ci in the pipeline fails on findings (exit 2) and on an empty scan (exit 3).
  • -Answers stay usable. Identifiers inside fenced code blocks go out as stand-ins and come back byte-exact, so the code the model writes still uses your names.
  • -Measure before you mandate. Run it on your own repo for a week. pretense audit shows what it swapped and when.

Try it on your own repo: create a free account, then run npm i -g @pretense/cli and pretense run claude. If you need a security review first, talk to me.
