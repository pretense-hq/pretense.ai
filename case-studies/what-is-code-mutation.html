What Is Code Mutation and Why It Beats Redaction for AI Security

Code mutation replaces proprietary identifiers with semantically equivalent synthetics before sending to LLM APIs, preserving context so the AI still produces useful output. Here is how it works and why it is the right architectural choice.

  • 7 mins read

  • |

  • Published Nov 7, 2026

The Problem With Removing Information

The instinct behind redaction is correct: keep proprietary information out of the prompt and it stays out of reach. The problem is implementation. When you strip identifiers out of code, you produce nonsense that the LLM struggles to reason about.

Consider a function that processes a payment:

async function processPaymentIntent(
  customerId: string,
  amount: number,
  paymentMethodId: string
): Promise<PaymentResult> {
  const customer = await customerRepo.findById(customerId);
  return stripe.createIntent({ customer, amount, method: paymentMethodId });
}

Strip out the proprietary names, the way redaction tools do, and you get:

async function [REDACTED](
  [REDACTED]: string,
  amount: number,
  [REDACTED]: string
): Promise<[REDACTED]> {
  const [REDACTED] = await [REDACTED].[REDACTED]([REDACTED]);
  return [REDACTED].[REDACTED]({ [REDACTED], amount, method: [REDACTED] });
}

Every LLM gets stuck on that. The structural and semantic relationships that make the code meaningful are gone. You asked for protection and got a broken prompt.

What Mutation Does Differently

Code mutation keeps the information and transforms it. Every proprietary identifier is replaced with a synthetic that follows the same structural rules, preserves the same token positions, and maintains the same relationships.

The same function through Pretense:

async function _fn4a2b(
  _v9k1m: string,
  amount: number,
  _v3b8c: string
): Promise<_cls7d1e> {
  const _v2f5a = await _cls6e3b._fn8c2d(_v9k1m);
  return _cls1a4f._fn2b7c({ _v2f5a, amount, method: _v3b8c });
}

An LLM reading this sees a payment processing function. The structure is intact. The parameter types are visible. The Stripe integration pattern is clear. The LLM can reason about this code and produce useful output. When the response comes back referencing _fn4a2b, Pretense swaps every identifier synthetic back to the real identifier, byte-exact, before returning the result to your IDE.

The Algorithm

Pretense uses deterministic SHA-256 hashing to generate synthetics:

function mutate(identifier: string, kind: 'fn' | 'v' | 'cls'): string {
  const hash = sha256(identifier).slice(0, 4);
  return `_${kind}${hash}`;
}

Determinism is the core property. The same identifier always maps to the same synthetic, within a session and across sessions. This enables three things:

  1. -Byte-exact identifier swap-back. The stored map contains every mutation, so swap-back is a direct lookup with zero reconstruction involved.
  2. -Cross-session coherence. If you ask Claude about processPaymentIntent in ten separate conversations, it always sees _fn4a2b. The model builds consistent understanding while the real name stays on your machine.
  3. -Auditability. Every mutation is logged: original identifier, synthetic, timestamp, file path, model, user.

What Gets Mutated (And What Passes Through)

Pretense is conservative by design. It mutates only the identifiers that reflect your proprietary domain model:

  • -Function and method names
  • -Variable names in function scope
  • -Class and interface names
  • -Type alias names

It passes these through as written:

  • -String literals (user-visible content; mutating breaks output quality)
  • -Comments (preserved verbatim for LLM context)
  • -Import paths (required for module structure reasoning)
  • -Standard library names (Array, Promise, Error, etc.)
  • -Language keywords

This boundary matters. String literals often contain user-visible text or configuration values that need to survive the round trip intact. Comments give the LLM context about intent. Import paths tell it what libraries are in use. Mutating these would degrade output quality while adding little real security.

Redaction vs Mutation: The Quality Gap

Industry data from teams that have used both approaches shows a significant output quality difference:

MetricRedactionMutation (Pretense)
LLM produces compilable output31%94%
Suggestions ship with zero rework22%89%

Proprietary identifiers in transit0%0%

Both approaches achieve the security goal. Mutation also preserves developer productivity.

Why This Matters for Enterprise Buyers

Security tools that degrade productivity stall at adoption. Developers route around them. A redaction tool that breaks 70% of AI completions will have 0% adoption within six weeks. Mutation-based protection achieves the same security outcome while preserving the productivity gains that made AI coding tools worth adopting in the first place.

This is why mutation is the right architectural choice: it is the approach security teams can actually enforce, because developers have every incentive to keep using it.

How I run Pretense on my own code

I build Pretense with Claude Code, and my sessions run through it. Here is the setup I give a new engineer, in order.

  1. -Run the agent through the proxy. Type pretense run claude where you would type claude. It starts a local proxy on port 9339, points Claude Code at it and stops the proxy when the session ends. Detected secrets and PII leave the laptop as stand-in tokens.
  2. -Put hooks on every repo. pretense install adds a pre-commit and a pre-push hook. A key that never lands in git is a key an agent never reads.
  3. -Scan before an agent reads the repo. pretense scan path . lists what it finds. In CI, pretense scan ci exits 0 when clean, 2 on findings and 3 when it examined nothing. Treat 3 as a failure.
  4. -Preview the swap. pretense review . shows what would be mutated. pretense mutate <file> --preview prints one file mutated and leaves the file on disk as it was.
  5. -Round-trip a file you need to share. pretense mutate <file> --map <map> swaps the secrets in place. pretense reverse <file> --map <map> turns it back into the original, byte for byte, from the encrypted map on your machine. We run that round trip on real files before every CLI release and compare sha256 hashes.

One thing I learned the hard way: inside a session the agent sees stand-ins, so a file the agent writes can hold a stand-in where you expected a real value. Grep what the agent wrote before you ship it.

What Pretense will not do is put a secret back into the model's answer. Code identifiers come back byte-exact. Secrets and PII stay as stand-ins in the response. That is deliberate: a prompt-injected model can echo a token into a link, and reversing it there would hand over the real key.

What this means if you lead an engineering team

The outcome: your team keeps asking AI assistants about real systems, configs and connection strings, and detected secrets leave each laptop as stand-ins.

  • -No new workflow. Engineers type pretense run claude in place of claude. Other AI CLIs run the same way, for example pretense run gemini.
  • -Guard the repo as well as the prompt. pretense install adds pre-commit and pre-push hooks. pretense scan ci in the pipeline fails on findings (exit 2) and on an empty scan (exit 3).
  • -Answers stay usable. Identifiers inside fenced code blocks go out as stand-ins and come back byte-exact, so the code the model writes still uses your names.
  • -Measure before you mandate. Run it on your own repo for a week. pretense audit shows what it swapped and when.

Try it on your own repo: create a free account, then run npm i -g @pretense/cli and pretense run claude. If you need a security review first, talk to me.
